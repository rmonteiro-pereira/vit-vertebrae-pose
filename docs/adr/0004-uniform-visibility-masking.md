# ADR 0004 — Every loss honours the visibility channel

**Status:** accepted · 2026-07 · **behaviour change** relative to the archived runs

## Context

Targets carry a visibility channel: `(x, y, v)` with `v = 0` meaning absent. Absent
landmarks — genuinely occluded, cropped out by augmentation, or padding to a fixed slot
count — are written as `(0, 0, 0)`.

Of the eleven loss functions in the original repository, five filtered on visibility
before computing the error (`euclidean`, `mse`, `l1`, `huber`, `multithreshold_improved`,
`cosine`). The other six did not:

```python
def exponential_loss_keypoints_simple(pred_keypoints, target_keypoints, ...):
    pred_px = pred[:, :, :2] * image_size
    target_px = target[:, :, :2] * image_size
    dists = torch.sqrt(torch.sum((pred_px - target_px) ** 2, dim=-1) + 1e-8)
    # no visibility mask
```

For those six, an absent landmark became a target at the top-left corner of the frame.
The optimiser dutifully pulled predictions toward `(0, 0)` in proportion to how many
slots were padded.

The exposure was bounded — the benchmark uses two landmarks, both usually visible, and
all 143 grid runs use `l1`, which masked correctly. But `focal`, `wing`,
`adaptive_wing` and `exponential` runs exist in the archive, and crop jitter can and
does mark a landmark invisible.

## Decision

Visibility masking moves into one shared helper, `_to_pixels`, that every loss calls
first. There is one implementation of "which landmarks count", and it is the same for
all ten objectives and for both metrics.

`tests/test_losses.py` parametrises over the whole registry and asserts, for each loss,
that adding an invisible landmark does not change the value, and that a fully invisible
batch returns a differentiable zero rather than raising or detaching the graph.

## Consequences

**This changes behaviour relative to the archived runs.** A `focal` or `wing` run
retrained with this package will not reproduce its archived number. The affected runs
are outside the published grid, so no published number is affected, but the
discrepancy is real and is recorded here rather than left to be discovered.

The differentiable-zero detail matters more than it looks. The original code returned
`torch.tensor(0.0, requires_grad=True)` for an empty batch — a *new* leaf tensor,
disconnected from the model. Calling `.backward()` on it produces no gradient anywhere
and no error either, so a batch in which nothing was visible would silently contribute
nothing while appearing to train. The replacement, `(pred * 0.0).sum()`, keeps the graph
connected.

## Alternatives rejected

**Leave the six losses as they were, to preserve exact archived behaviour.** Rejected:
the archive is shipped as data and is not regenerated by this code (ADR 0005), so
bug-compatibility buys nothing and would ship a known defect.

**Make masking opt-in per loss.** Rejected — it is a property of the target
representation, not of the objective. Eleven independent decisions about the same
question is how the inconsistency arose in the first place.

**Drop the four unmasked losses entirely.** Tempting, since none is used in the
published grid. Rejected because the loss comparison is part of what the project set
out to study, and a fixed implementation is more useful than a missing one.

## What would reverse this

Nothing. If exact reproduction of a specific archived non-L1 run is ever needed, the
right move is a documented compatibility flag on that run, not a return to eleven
divergent implementations.
